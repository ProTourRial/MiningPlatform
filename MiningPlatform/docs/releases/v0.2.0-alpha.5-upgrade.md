# Upgrade Verification: v0.2.0-alpha.4 to v0.2.0-alpha.5

Author: Abia Nugrahanto  
Date: 2026-07-31

## Safety rules

- Never test migrations against the only copy of a production database.
- Create two disposable databases: one empty database and one restored copy of alpha.4.
- Back up the alpha.4 database before applying the alpha.5 migration.
- Run commands from the repository root, not directly from inside the ZIP archive.

## 1. Source and dependency verification

```bash
corepack enable
corepack prepare pnpm@10.13.1 --activate
pnpm install --frozen-lockfile
pnpm db:generate
pnpm typecheck
pnpm test
pnpm build
```

Equivalent release command:

```bash
pnpm verify:alpha5
```

The command must run in an environment with network access for the first package installation and permission to execute the Prisma engine for the operating system.

## 2. Fresh database migration

Create a new empty PostgreSQL database, for example `miningplatform_alpha5_fresh_verify`. Do not reuse a database containing valuable data.

```bash
export DATABASE_URL='postgresql://USER:PASSWORD@HOST:5432/miningplatform_alpha5_fresh_verify'
export MIGRATION_TEST_ACK='alpha5-fresh-empty-database'
pnpm verify:migration:fresh
```

Expected result:

- every migration is applied in order;
- Prisma reports that the database schema is up to date;
- `WorkerCredentialStatus` exists;
- `WorkerCredential` exists with its unique and foreign-key constraints;
- no migration row has a failed status.

## 3. Upgrade migration from alpha.4

Prepare a disposable database that is genuinely at alpha.4 schema state.

Recommended procedure:

1. Restore an alpha.4 backup into a new database such as `miningplatform_alpha4_upgrade_verify`.
2. Confirm the alpha.4 application can read that database.
3. Switch the source tree to alpha.5 without changing the database manually.
4. Run:

```bash
export DATABASE_URL='postgresql://USER:PASSWORD@HOST:5432/miningplatform_alpha4_upgrade_verify'
export MIGRATION_TEST_ACK='alpha4-upgrade-copy'
pnpm verify:migration:upgrade
```

5. Run `pnpm db:generate`, `pnpm typecheck`, and the production-authentication integration test when PostgreSQL and Redis are available.

Expected result:

- only the alpha.5 migration is newly applied;
- existing users, mining accounts, workers, shares, ledger rows, and audit logs remain intact;
- `WorkerCredential` starts empty until credentials are created;
- no legacy `Worker.passwordHash` value is modified by this migration;
- the application can create, rotate, revoke, and authenticate a worker credential.

## 5. Release acceptance

Alpha.5 is accepted only after all of the following pass in the same environment:

```text
[ ] pnpm install --frozen-lockfile
[ ] pnpm db:generate
[ ] pnpm typecheck
[ ] pnpm test
[ ] pnpm build
[ ] fresh database migration
[ ] alpha.4 upgrade migration
[ ] canonical ADR static check
[ ] no obsolete ADR duplicates
```

## 6. Release manifest and diagnostics

Verify the extracted payload manifest:

```bash
pnpm release:manifest:verify
```

Check API diagnostics after startup:

```bash
curl http://localhost:4000/version
```

Check a service binary without starting it:

```bash
pnpm --filter @mining/stratum-server start -- --version
```

List worker credentials without exposing secret material:

```bash
pnpm worker:credential list demo.worker1
```
